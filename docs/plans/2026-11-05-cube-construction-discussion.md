# cube 构建讨论：先确定模块边界和首个交付流程

2026-11-05。状态：讨论稿；只记录建议和已确认约束，未代表用户接受全部设计，也未开始新功能实现。基于当前 `4e13e03` 的代码与[总体设计](2026-11-05-cube-carrier-transport-design.md)。

## 已确认约束

- 产品名 cube，首批对象为有机晶体、非晶、聚合物。
- 保留 Python、C++、Rust、Fortran 的独立计算核心；Python 使用 uv。
- 当前已有通用事件内核、基础速率、单载流子图和真实体系验证；统一材料工作流、多载流子、量化自动化尚未完整实现。

## 本轮建议：围绕统一材料状态组织软件

选择“一个 Python 工作流＋统一材料状态＋四个计算后端”，将数据、物理与计算连接起来。

这里的材料工作流是通用 KMC 的一个应用层。通用核心仍按“状态、事件、速率、状态更新、观测”组织，不能要求每个 KMC 问题都具备分子、dimer 或载流子。反应、扩散及其他随机事件模型可直接使用核心；材料模块把自己的物理状态编译成相应事件模型。GPU 后端按模型声明能力，不把材料图批轨迹的实现宣传为任意 Python 回调的 GPU 执行器。

| 层 | 拥有的数据/责任 | 首要边界 |
|---|---|---|
| 材料 | 晶胞、原子到分子/电子片段映射、位点、镜像边、链连接、V/λ/形成能及来源 | 这是物理输入，不由 KMC 内核推断 |
| 运行状态 | 载流子种类/占据、物理时间、累计位移、随机流 | 与不可变结构分开，为后续多载流子保留明确位置 |
| 物理模型 | 温度/场/环境与相互作用、正反自由能差、速率提供者 | 速率是物理输入和运行条件的派生量；缓存须可失效 |
| 求解器 | 通用 SSA、材料出边 KMC、单粒子确定性解 | 共用同一率定义，支持独立正确性核对 |
| 工作流/分析 | 导入、参数任务、运行、统计、检查点、报告 | 用户有一个入口；各后端不重复实现整个前处理 |

现有 KMC1 只包含图/反应与已生成速率，没有充分表达原始电子参数和来源。因此长期材料状态应另有版本化规范，KMC1 保留为低层回归/交换输入。改变温度或场时，应由原始参数重新生成率，不能复用未注明条件的旧率文件。

### 为什么推荐这个边界

- VOTCA 的能量/速率/输运分层适合管理物理定义；cube 将其转化为自己的接口。
- MorphCT 的电子片段思想适合聚合物，但片段划分必须显式并可检验。
- CharTED 的占据、库仑和物理事件组织值得借鉴；其规则晶格与经验尝试频率作为一种可选材料模型，不规定所有 cube 数据。
- mcal 的确定性张量计算表明，同一材料网络可由第二种求解器验证；共享物理定义比只共享一个 mobility 字段更有价值。

参照的是固定提交的[源码研究](../research/source-review.md)，不是直接引入上游实现。

## 可选路线与取舍

1. **共享材料状态＋独立后端（建议）**：一套参数来源与工作流，四语言实现共同的计算契约；需先设计数据与接口。
2. **所有领域信息都由用户事件回调管理**：保留最大建模自由，但用户需自行拼接单位、几何、参数、分析与来源，不适合作为默认材料工作流。
3. **四种语言各做完整应用**：每套可独立覆盖前处理到报告，但会重复维护解析器、量化调度和统计定义，且容易产生行为差异。

通用事件接口继续保留，供特殊模型扩展；独立后端也继续保留，不因共享前端而缩减为演示实现。

## 用户已确定：首个可独立交付版本的优先流程

本轮只讨论实现先后，长期目标不变：

- A（建议）：已有结构和电子参数 → cube 计算速率 → bulk KMC/确定性核对 → 迁移率张量与收敛报告。
- B：从结构开始，优先量化任务生成、调度、解析和参数计算自动化。
- C：先完善多载流子、占据、库仑和器件输运。

用户最初选择 A：已有结构与电子参数 → cube 计算速率、迁移率和收敛报告。输入包括 V、λ、位点形成能及其来源；跃迁速率由 cube 计算。用户后续进一步要求从 MD 单帧开始生成电子参数，因此当前目标已包含 B 中的结构提取和量化自动化，具体以文末更新及独立工作流文档为准。用户已确定首版先验证独立单载流子轨迹；C 中的有限浓度相互作用保留扩展接口，不作为首版已支持的功能。


## 首版数据契约建议（待细化为正式 schema）

统一导入层生成以下对象；Python 和原生后端共享含义与单位转换规则：

1. 晶胞：三条晶格矢量、周期方向与结构来源。
2. 位点：稳定编号、坐标、分子/链/电子片段映射、载流子形成能与来源。
3. 跃迁对：起终点、整数晶格镜像、V、成对 λ、链内/链间标签和来源。计算出的零耦合与缺失值分开。
4. 运行条件：载流子、温度、场、初态、平衡与观测时间、随机流、后端和停止条件。
5. 结果：定向速率和检查、固定物理时间观测、扩散/迁移率张量、漂移速度、统计区间、适用假设与收敛状态。

已有 CSV 可以作为导入适配器的一种输入，不让某个特定 CSV 列名成为通用材料模型。原始能量/耦合/重组能保留，温度或场变化后重新生成速率。缺少位点能时仅允许显式选择“等位点能近似”，结果记录这一假设，不将缺失值自动转换为物理零。

首版验收应至少覆盖：当前 e_006 回归、非均匀位点能与详细平衡、正反小场、一般周期镜像和三斜晶胞、两态/游走解析模型以及四语言一致性。规则晶格可作为独立的可控测试输入，通过同一网络规范进入求解器；真实结构输入仍为首批用户流程。

## 已确认：首版先验证独立单载流子轨迹

用户已明确选择首版验证独立单载流子轨迹。材料工作流以稀释极限贯通，GPU 并行独立轨迹，每条轨迹拥有独立的状态、物理时间和随机流；轨迹之间不加入占据排斥或载流子间库仑相互作用。共享的只读速率网络不等于共享的多粒子状态。按单粒子模型的适用条件使用确定性解与解析模型验证输运算法。

通用 KMC 内核仍按状态与事件组织，不把一个全局载流子位置硬写进公共引擎。未来有限浓度模型需要独立声明占据状态、允许事件、相互作用能和速率缓存失效；独立单载流子批处理不自动升级为这一模型。该区别属于模型能力，不能通过改一个轨迹数参数隐式切换。

## 与浓度选择无关的工程构建建议

### 现有工程核对

当前 `scripts/build.py` 直接构建 C++/Fortran 并调用 Cargo；`scripts/check.py` 串联原生测试、跨语言测试和 uv 打包。`CMakeLists.txt` 是另一个可选入口，但 `project(... LANGUAGES CXX Fortran)` 会同时要求两种编译器，且构建配置与 Python 脚本分别维护。现有 Fortran 检查构建含 `-fcheck=all`，性能脚本另建不带该检查的优化版本。Python 包目前不依赖原生扩展即可使用。

这些是核对当前代码的观察；本节没有改动构建脚本，也没有声称 CMake 已通过实际构建验收。

### 建议的职责划分

| 工具/入口 | 负责范围 | 应避免的重复 |
|---|---|---|
| uv / pyproject | Python 环境、锁文件、Python 包和命令入口 | 不再手写第二份 Python 依赖列表 |
| CMake（验证后采用） | C++/Fortran 库、可执行文件、安装规则和编译测试配置 | Python 构建脚本不再重复维护同一套原生编译参数 |
| Cargo | Rust 库/程序、依赖与编译配置 | 不在 CMake/Python 中手工列出 Rust 源码编译依赖 |
| `scripts/` 开发入口 | 调用以上工具、收集测试、生成构建/运行元数据 | 负责调度，不充当第四种编译系统 |

原生后端应可单独构建，C++ 用户不需要先安装 Fortran，反之亦然。开发者验收矩阵覆盖四种语言；普通使用者可只安装需要的后端。Python 安装保留可独立工作的参考核心。

首个集成阶段建议采用进程/版本化文件协议，先验证端到端行为和数据边界；后续有调用成本证据时再加入绑定或窄 C ABI。原生 ABI 不应直接暴露 Python 对象、C++ vector、Rust trait 对象或 Fortran 派生类型的内存布局。

### 公共后端契约

- 能力查询：后端和协议版本、支持的物理模型/观测协议、浮点类型、编译器和构建配置。
- 输入：已经规范化的材料状态和运行配置，不要求每种语言直接解析所有上游量化软件格式。
- 输出：带状态的机器可读结果、物理时间、实际事件数、随机源信息、观测量与停止原因。
- 错误：输入不完整、单位/镜像错误、不支持的功能、数值失败、资源/时间上限、尚未收敛分别表达；不能都输出为零迁移率。
- 恢复：若声明支持检查点，必须保存足以恢复随机流和求解状态的数据；不支持时明确拒绝，不能只保存当前位置就称可续算。

同一规范在四个核心中独立实现；前端只按能力选择和调用，不静默替换求解器。公共契约引用模型自己的状态规范，首版材料模型采用独立单载流子状态；未来多粒子状态通过另一个模型能力接入，而不是改变“轨迹数”的含义。

首版拟议的状态边界如下；这些字段是协议设计，不是已实现的 ABI：

| 对象 | 内容 | 共享与修改规则 |
|---|---|---|
| 不可变网络 | 晶胞、位点、带镜像位移的出边、固定运行条件下的速率及来源 | 同一批轨迹可共享；温度、场或参数改变时重新生成/校验 |
| 单条轨迹 | 当前位点、物理时间、累计位移、事件数、随机流/计数器、停止状态 | 仅由该轨迹更新，不能复用另一轨迹的随机状态 |
| 观测配置 | 初态、平衡与观测时间、观测时刻、停止条件和统计定义 | CPU/GPU 使用相同定义；事件序号不能代替物理时间 |
| 批次与结果 | 轨迹身份、任务/随机流分配、观测结果、未完成/失败原因与汇总 | 批大小或设备调度不应改变模型；检查点必须保存各轨迹恢复所需状态 |

现有参考引擎只声明支持状态相关、时间齐次的跳跃过程。未来随物理时间连续变化的率需要单独的时钟/算法能力，不能只在每次跳跃时读一次率就宣称支持一般时变 KMC。GPU 模型也不能假设能执行任意 Python 回调。

### 构建配置建议

1. Debug：开发期边界/运行时检查与调试信息，检查参数按编译器配置。
2. Reference：用于回归，固定算法、事件顺序、参考随机流与保守浮点设置；数值一致性按声明的容差，而非承诺任意平台逐位相同。
3. Release：优化构建，保留显式数值/输入合法性检查；默认不启用会改变 NaN/无穷语义的 fast-math。

性能比较使用相同配置类别，另外记录快照、输出和启动成本。架构特定优化与激进浮点选项如引入，需显式开启、记录并另做正确性验收。

### 测试与交付层次

| 层 | 要证明的内容 |
|---|---|
| 数据/物理测试 | 单位转换、周期镜像、正反自由能差、详细平衡和缺失参数策略 |
| 后端协议测试 | 同一材料数据可分别运行；能力与不支持错误可核对 |
| 算法测试 | 等待时间/选择概率、吸收态、截止时间；适用条件下对照解析或确定性解 |
| 四语言对照 | 相同算法与参考流的事件/状态/时间；优化后算法改变随机消耗时改做分布与观测量对照 |
| 材料回归 | e_006 加晶体/非晶/聚合物的逐步扩展案例，明确哪些是实际完成的案例 |
| 安装与打包 | 从 wheel/sdist 和原生安装产物运行样例，验证无需依赖开发目录 |
| 性能 | 内核/格式化/磁盘和前处理分开，保留所有重复测量与正确性摘要 |

CI 先执行轻量确定性与后端测试，较长统计/性能检查分任务运行；已发布案例只使用明确允许公开的输入。外部量化程序未安装时，其解析器仍可用合法的小样例测试，完整任务测试独立标记。

### 建议的代码组织（未来布局，尚未执行重排）

```text
src/cube/             Python 材料、物理、工作流和分析
src/universal_kmc/    保留兼容的通用参考内核
cpp/                  C++ 计算库和命令入口
rust/                 Rust 计算库和命令入口
fortran/              Fortran 计算库和命令入口
schemas/              材料状态、运行与结果协议
examples/             小型材料工作流与解析验证例子
tests/                物理、协议、端到端和跨语言测试
benchmarks/           有正确性摘要的独立性能测量
scripts/              开发构建、验证和资料复现入口
docs/                 理论、接口、使用与验证证据
```

工程默认先 CLI/Python API，图形界面可消费同一协议。文件格式、错误状态和安装测试先稳定，之后再决定 GUI 的技术栈。


## 用户后续补充：完整 MD→量化→GPU 输运流程

用户进一步明确要求：GROMACS 和 LAMMPS 的 MD 单帧；按分子内共轭平面的指定原子编号筛选、提取 dimer；计算转移积分及 QM/MM 重组能；GPU 同时用于量化和 KMC。此补充扩展了首个用户工作流，不能将前述选择 A 解释为最终只支持导入已有参数。更新设计及待确认的距离定义见 [MD/量化/GPU 工作流](2026-11-05-cube-md-quantum-gpu-workflow.md)。原构建分层仍适用，新增统一结构适配器、QM/MM 任务层、显存调度及独立 GPU KMC 后端。

用户随后确定：首个 GPU QM/MM 重组能验证固定周围 MM 分子，只优化 QM 分子。该模式的四点任务、固定环境检查、能量/梯度与 CPU/GPU 对照要求已记录在上述工作流文档中；环境结构松弛仍为后续可扩展模式。具体 QM 方法与力场尚未指定，不将这项选择误写为已运行通过。
